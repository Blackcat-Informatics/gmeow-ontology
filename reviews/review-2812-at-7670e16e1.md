### R1 (REQUIRED): a tuple whose argument is another tuple's reifier is still an unnamed execution failure (exit 5), and the compiler can produce it

What I read:
- relational_core.rs:1940-1996: `formula_atom_to_rc_atoms` passes any binary head atom through unchanged, including one on `logic:naryArg{i}`. The branch relies on this itself: relational_core/tests.rs:298 and prove_cli.rs:348 author `logic:naryArg0` in a consequent.
- head.rs:61-71: `∃U,V` becomes `?existH0`, `?existH1`, in authored order.

Construction (selected source, `logic:exists` as in probe p4):
`∀A. Src(A) → ∃U,V. instanceOf(U, ex:R1) ∧ naryArg0(U, V) ∧ instanceOf(V, ex:R2) ∧ naryArg0(V, A)`.

`reified_nary_head_groups` accepts it. Both groups are typed, each has an existential subject, and the indices are contiguous. At firing (chase.rs:467-488):
1. `?existH1` is skipped by the value-null pass because it is a reifier.
2. Groups are minted in `BTreeMap` order, so `?existH0` comes first.
3. `eval_term_value(?existH1)` fails with `chase: n-ary head argument variable "?existH1" unbound after body join` (chase.rs:1063-1071).

prove then reports `NATIVE_EXECUTION_FAILED`, exit 5. The message names a variable, not the rule or its relations, and carries no `RefusedRuleHead` payload. This is the defect class the issue was filed for (problem point 1, and box 3's "never an execution failure"). With the binders swapped, the same head mints correctly, so the outcome depends on variable order.

The new doc comment says the firing loop binds each reifier to its minted node (chase.rs:929-932). That is false for this case. The claim that the compiler cannot produce this shape is also false. Only the `Term::App` route is closed (relational_core.rs:2066).

Required change: either mint the groups in dependency order (a referenced reifier first) and have `validate_head_shape` refuse a reifier cycle with a `RefusedRuleHead`, or have `validate_head_shape` refuse a reifier used as a tuple argument. Either way, add a test for the authored nested case.

I did not execute this. It comes from reading the code at 7670e16e1, and the input is not one of probes p1-p6.

## Answers to the review brief's questions

1. **The typing-only group refusal was dropped: is that right?** Yes. The removed `args.is_empty()` refusal fired only when some `naryArg` atom appeared elsewhere in the head. Without one, the same atom was already accepted as a typed witness, so the refusal was incidental, not a protection. A typing atom with no positional atoms is just the unary predication `Rel(z)` under the HiLog reflection. The "existential subject" case in the chase test covers it. I could not build a malformed tuple that now passes silently: a tuple exists only through its `naryArg` atoms, and every refusal that guards the mint is still present (non-variable or body-bound reifier, non-constant relation, missing or duplicate typing atom, gapped or duplicate indices). One check exists neither before nor after: an arity shortfall against a declared arity, since the chase knows no arity.
2. **Is it consistent to leave `boundaries` empty on failure?** Yes. An execution failure uses the refused framing: completeness `unknown`, preservation `unsupported([])`, information `not-evaluated`. `boundaries` is the boundary account of a decided run. Filling it from a partial drop list would present that partial list as the account. The partial drops belong in `selection`, marked incomplete, which is what the change does. The text defect is R2, not this.
3. **Is a unit-only box-4 test acceptable?** The unit test protects the constructor. The wiring in `prove()` has no test: the OWL-leg failure carrying `native.claims_read`, and the drops passed through. Honest CLI-level failure inputs do exist:
   - R1's nested authored-reifier head works today, but a fix for R1 removes it.
   - A selected `logicx:ExistentialRule` source record whose head the chase refuses would probably also work. The path is `prepare_reasoning_input` → `source_existentials::Collector`, then `PreparedChaseRule::from_source`, then `RefusedRuleHead`, then `NATIVE_EXECUTION_FAILED`. Formula lowering does not see that path, so a hard failure there matches the record grammar's other refusals. It would also exercise the O5 evidence projection. I have not executed this.

   I judge unit level acceptable for the contract, but weaker than what is available (optional).
