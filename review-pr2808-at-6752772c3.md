## Is each corrected statement true?

### 1. The upper bound (`memory_record.rs:106-111`, `RUST-OPTIMIZATION.md:112-118`)

True.

Write the resident size as non-allocator resident memory plus the resident part of live allocations plus resident free chunks. Subtracting the live bytes leaves non-allocator resident memory plus resident free chunks, minus the live bytes that are not resident. That is at least the resident free memory whenever all live bytes are resident. So both parts hold:

- It is an upper bound because of the non-allocator term: code, stacks, file and shared mappings. VmRSS is RssAnon + RssFile + RssShmem.
- The author's qualifier is needed: swapped-out live pages, and live pages that were never touched (including untouched mmapped chunks counted in `hblkhd`), lower the figure and can break the bound.

"Not a measure of what a return can recover" is also true. A return frees only whole pages inside free chunks. `mtrim` does not shrink the top chunks of non-main arenas.

There is one small hole, too small to matter. glibc counts free chunks held in per-thread tcaches as in use (`uordblks`), so that slack is subtracted as if it were live. The cap is 7 chunks for each of 64 size classes up to 1032 B, roughly 230 KiB per thread at most. See OPTIONAL-1.

### 2. The readings around a return (`scheduler.rs:76-85`, `RUST-OPTIMIZATION.md:107-109`)

True.

The mutex serializes only `reclaim_allocator_slack` callers, so one return's two readings never overlap another return. Workers keep allocating and freeing between the two readings, so the difference is net of their activity and can be small or negative. The PR body now says the same.
