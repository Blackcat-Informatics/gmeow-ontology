# Notes & Annotation — alignment & projection reference

The first-class annotation and personal-knowledge-management layer. A person's digital
existence includes their *notes* — annotations, highlights, bookmarks, comments, and the
linked web of thought (Zettelkasten / PKM). This slice unifies scattered GMEOW pieces
(documents, sources, EvidenceSpan, aboutness, standpoint) into a coherent annotation layer
that **reuses, never duplicates** existing constructs.

Everything here is **authored once** in `mapping-dsl/` and generated by
`gmeow compile-mappings` (Principle 4); nothing in `mappings/`, `projections/`, or
`queries/projections/` is hand-edited.

## Core design

1. **A Note is content; an Annotation binds it to a target** (the W3C Web Annotation idiom:
   Body / Target / Motivation). A highlight = target + selector, no body; a bookmark =
   `motivatedBy bookmarking`; a comment = a Note replying to a target.
2. **One selector model, reused.** The annotation target's selector **is** the
   `EvidenceSpan` / `Selector` (text quote, text position, page, locator). `Selector` is a
   subclass of `EvidenceSpan`; no second selector model is minted.
3. **Aboutness is a Tagging, not a string.** A note's topic reuses `isAbout` / `Tagging`
   from the tags building block.
4. **Backlinks are first-class and bidirectional** (the RDF gap): `mentions` / `mentionedIn`
   (inverse), `relatedNote` (symmetric) — kept out of OWL cardinality for DL regularity.
5. **Perspectival + suppressible:** notes are `accordingTo`-indexed; a retracted note sets
   `displayable false`, never deleted (Principle 10).

## Projections — the four-artifact stack

### W3C Web Annotation → `queries/projections/web-annotation.rq`

Re-expresses GMEOW Annotation / Highlight / Bookmark / Comment as `oa:Annotation`.
Standpoint, provenance, confidence, temporal scope, and suppression state are
dropped; the projection is intentionally flat (no `dcterms:creator` emitted).

| Branch | CONSTRUCT | Lossy drop |
|---|---|---|
| Annotation | `oa:hasBody`, `oa:hasTarget`, `oa:motivatedBy` | provenance, confidence, temporal scope, standpoint |
| Highlight | `oa:hasTarget` → `oa:SpecificResource` + `oa:hasSelector` | body absent by design; selector precision dropped if not projected |
| Bookmark | `oa:hasTarget`, `oa:motivatedBy oa:bookmarking` | body and selector absent by design |
| Comment | `oa:hasBody`, `oa:hasTarget` (parent), `oa:motivatedBy oa:replying` | thread depth, reply tree, standpoint, confidence, temporal scope |

### schema.org → `queries/projections/schema-org.rq`

Re-expresses Note → `schema:NoteDigitalDocument` (Comments included by subsumption).

| Source | Target | Lossy drop |
|---|---|---|
| `gmeow:Note` | `schema:NoteDigitalDocument` | standpoint, confidence, temporal scope, suppression, aboutness, tagging |
| `gmeow:Comment` | `schema:NoteDigitalDocument` (+ `schema:parentItem` when `commentParent` present) | same + reply tree depth + Comment-specific type (collapsed to avoid rdflib UNION-depth limit) |

### ActivityStreams → `queries/projections/activitystreams.rq`

Re-expresses Note → `as:Note` for fediverse / decentralized syndication.

| Source | Target | Lossy drop |
|---|---|---|
| `gmeow:Note` | `as:Note` | standpoint, confidence, temporal scope, suppression, aboutness, tagging, backlinks |

### Markdown / `[[wikilink]]` → `queries/projections/markdown.rq`

The GMEOW-native bridge to Obsidian / Logseq PKM interop. Projects `mentions` and
`relatedNote` to a flat `gmeow:hasWikilink` graph.

> ⚠️ **Brutally lossy.** This projection drops **ALL metadata**: standpoint,
> confidence, temporal scope, suppression state, aboutness, tagging. Only the directed
> (`mentions`) and undirected (`relatedNote`) wikilink edges survive. The round-trip
> from RDF → Markdown → RDF cannot recover the rich annotation layer; it is a
> deliberate downcast for human PKM consumption (Principle 4).

## PKM round-trip guide

**Obsidian / Logseq conventions.** A note file is a Markdown document. Wikilinks are
`[[Note Title]]` or `[[Note Title|Display Text]]`. GMEOW projects a note's
`rdfs:label` or `noteContent` first line as the file title, and its `mentions` /
`relatedNote` edges as wikilinks in the markdown body. On re-ingest, the markdown
parser mints `gmeow:Note` individuals and `gmeow:mentions` edges; the original
provenance, standpoint, and confidence are **not recoverable** and must be re-asserted
by the ingestion pipeline if needed.

## Term reference

### gmeow:Note · gmeow:noteContent · gmeow:noteAuthor · gmeow:noteCreatedAt · gmeow:noteModifiedAt

The content layer — an annotation body, Zettelkasten card, comment, or standalone
thought, grounded as an `InformationObject`. `noteContent` carries the flat 80%-case
text/markdown; `noteAuthor` (non-functional) the flat authorship shortcut, promotable
to a reified `Participation` when the act needs period, confidence, or standpoint (P9);
`noteCreatedAt`/`noteModifiedAt` are lightweight four-clock timestamps.

### gmeow:Annotation · gmeow:annotationBody · gmeow:annotationTarget · gmeow:annotationTargetSpan · gmeow:annotationMotivation

A reified binding of a body to a target with a motivation — the W3C Web Annotation
idiom as a `gufo:Relator`. `annotationBody` (functional, optional — highlights and
bookmarks have none) names the note; `annotationTarget` (functional) the annotated
entity; `annotationTargetSpan` (non-functional) reuses `EvidenceSpan`, no second
selector model minted; `annotationMotivation` (functional) the purpose, no value
privileged.

### gmeow:Highlight · gmeow:Bookmark

Specialized annotations: a `Highlight` marks an anchored span and carries no body (a
pure target+selector binding motivated by highlighting); a `Bookmark` records a target
resource for later retrieval, typically with no body or selector.

### gmeow:Comment · gmeow:commentParent · gmeow:hasReply · gmeow:hasDirectReply

A `Note` that replies to an annotation or another comment — a threaded discussion node.
`commentParent` names the one thing replied to (range `Entity`, so any annotatable
entity may be a parent); `hasDirectReply` (inverse of `commentParent`) is the immediate
reply, and its transitive superproperty `hasReply` reaches the full reply tree, kept
free of OWL cardinality for DL regularity.

### gmeow:mentions · gmeow:mentionedIn · gmeow:relatedNote · gmeow:hasWikilink

The first-class bidirectional backlink graph (the RDF/PKM gap). `mentions` is the
directed edge from a note to an entity; `mentionedIn` (its inverse) the backlink view,
materialized never hand-maintained; `relatedNote` (symmetric) an undirected associative
link; `hasWikilink` a Markdown/PKM round-trip edge projected from the others, not
asserted canonically.

### gmeow:AnnotationMotivation

The purpose for which an annotation is created — a VALUE vocabulary (individuals, never
subclasses) aligned to the W3C Web Annotation motivation set: describing, commenting,
highlighting, bookmarking, tagging, linking, questioning, replying, assessing,
moderating. Co-equal and open: no motivation is primary or default.

## Preserve a purpose as written

`purposeAsWritten` specializes the tags owner's `tagAsWritten` for a `Note`.
It retains an unresolved purpose in the writer's exact words, with supplied
language and RDF 1.2 direction. Untagged text remains a string; no language,
`Tag` or `AnnotationMotivation` is invented. A resolved motivation or purpose
can be recorded independently when justified. Several attributed wordings may
coexist; none is preferred.

## Working notebook kinds and writer assessments

A `NotebookEntry` is a working `Note`. Its content, notebook function and
writer assessment are distinct. Existing `noteContent`, `noteAuthor`, annotation
and provenance machinery remains applicable; an entry is neither an assertion
act nor an executable step.

`notebookEntryKind` uses the open `NotebookEntryKind` vocabulary:

| Kind | Working-note function |
| --- | --- |
| `notebookHypothesis` | Recording a conjecture. |
| `notebookBranch` | Recording an alternative line of inquiry. |
| `notebookDataInProcess` | Holding material being worked on. |
| `notebookNextStep` | Recording a proposed next action. |

An inquiry branch has no automatic software-branch identity or executable path.
Material in process supplies no runtime status. A next-action note creates no
`Intention`, command, admitted `PlanStep` or executable plan.

`notebookEntryState` uses the independent, open `NotebookEntryState` vocabulary:

| State | Writer's declared notebook assessment |
| --- | --- |
| `hypothesisUnderTest` | A hypothesis is under examination. |
| `hypothesisHeld` | A hypothesis is retained as a working candidate. |
| `hypothesisDropped` | A hypothesis is set aside from working consideration. |
| `branchOpen` | A line of inquiry remains open. |
| `branchClosed` | A line of inquiry is closed in the notebook. |

These are notebook assessments: under examination proves no test execution;
retaining a hypothesis proves no truth or mental belief; setting it aside
proves no falsity and deletes nothing. Closing a branch establishes no goal
completion. Neither kind nor state implies the other, and no allowed kind and
state matrix or automatic transition is imposed.

Scope each exact state assertion with `accordingTo` the actual writer Agent,
intentionally serving as the claim's frame. Keep the entry's `noteAuthor`
separate from `wasAttributedTo` the recording Agent and `wasDerivedFrom` the
source artifact on the state reifier. A recorder can preserve another writer's
assessment. Authorship and recording attribution alone supply neither the
writer frame nor authentication or write permission (Principles 9 and 11).

Both properties are nonfunctional and constrain only supplied values. Missing
metadata remains unspecified. Conflicting and historical state claims retain
their exact tuples, writer frames and provenance; no default, global winner or
latest-timestamp selection is inferred. Existing native RDF 1.2 `rdf:reifies`
can retain an entry's exact triple content without asserting that proposition.
Aboutness remains a separate subject-matter relation. No additional statement
field, state-assignment wrapper or permission protocol is introduced
(Principles 4 and 17).

The ordinary [notebook scene](examples/notebook-kind-state.ttl) records all four
kinds and five states, including competing writer assessments and retained
dated reports. Its recorder, writers and source artifacts remain distinct.
The quoted content is unasserted, and the scene reports no executed tests,
scheduler, state update or goal completion.

## Exact quoted notebook statements

`notebookStatement` retains an original native RDF 1.2 triple term on a
`NotebookEntry`. The exact same entry must have `rdf:reifies` with that exact
same term. A quote on another entry, substitute prose or an invented witness
cannot satisfy this binding. Preserve the original term and actual source
context without string conversion.

Quotation does not assert the quoted proposition or establish truth, mental
belief, an assertion act or execution. Native RDF 1.2 transport owns the
representation; the same-term law is not a generic triple-term validator.
The property is nonfunctional and has no declared range. Its global closure
selects the supplied subject's NotebookEntry domain without adding a required
statement to every notebook entry.

NotebookEntry still inherits Note's actual content-or-label requirement.
Preserve the supplied content or label rather than fabricating one for this
association. AgencyRecords owns the separate `notebookWorkingThrough` relation
from an entry to an actual Activity; it supplies no current-work verdict or
shared author/performer inference. Exact writer-state attributions remain
independent of authorship and recording attribution (Principles 4, 9, 11 and 17).
