# How GMEOW already models AI claims

GMEOW did not need an AI claim model bolted on — the constitution's unified
observation stance (P9) **is** one: *"a measurement, a standpoint-indexed claim,
and a sensory perception are the same reified construct (a claim made from a
vantage)."* This slice mints only the genuinely missing pieces (the retrieval
segment, the prompt artifact, the invocation activity, the model card, the
surfaced contradiction, the memory role) and documents how the EXISTING
machinery does the rest. Each pattern below is existing-terms-only unless
marked.

## 1. A generated claim is a query, not a class

An LLM output is a `gmeow:StandpointClaim` (⊑ `gmeow:Observation`) whose
`gmeow:vantage` is the model `gmeow:SoftwareAgent` and which
`gmeow:wasGeneratedBy` its `gmeow:ModelInvocation` (new) — a direct triple on
the claim individual. On the reified RDF 1.2 statement form, confidence /
`accordingTo` / the clocks ride statement annotations, and the invocation link
is `gmeow:mappedFrom` (the machine-derivation AnnotationProperty), because
axiom annotations stay AnnotationProperty-clean for the DL downcast (P3) — see
`dsl/statements/ai.ttl`.
"GeneratedClaim" needs no class: it is the query *claims whose vantage is a
SoftwareAgent and which were generated by an invocation*. The same claim
re-asserted by a person sheds nothing but that provenance.

## 2. Hallucination: flagged, never deleted — and named honestly

A claim node with no `gmeow:groundedIn` span (new) is a flagged hallucination
(P10: retained, surfaced by EvidenceSpan audit machinery's audit gates). The VERDICT about it is itself a
claim from a vantage:

- the auditor's `gmeow:claimModality gmeow:bullshit` — Frankfurt's category is
  already in the standpoint slice: asserted without regard to truth;
- or `gmeow:claimVeridicality gmeow:veridicalityUntrue` (deception slice) when
  the standpoint holds it settled-false;
- declared fiction/roleplay output is `gmeow:veridicalityLicensedFalsehood` —
  the licensed-falsehood safety property separates harmless fictional assertion
  from deception, for model outputs exactly as for human ones.

## 3. Evaluation is the norms slice's Assessment

`gmeow:Assessment ⊑ gmeow:Observation` (norms): *an LLM judge is just a
vantage*; two judges disagreeing are two coexisting cells with no winner. The
RAGAS/AIS metric family ships as a published `gmeow:Rubric` with `Criterion`
individuals in the eval suite — instance data, never TBox. This core
slice deliberately mints NO evaluation machinery.

## 4. Hallucination as hazard (risk extension, instance data)

`gmeow:Hazard` borne by a deployment, `gmeow:manifestedAsType` a hallucination
event type, grounding gates as `gmeow:Mitigation` — zero new TBox; see the
`ai-normative` fixture.

## 5. System prompts and personas (norms slice, doctrine)

A system `gmeow:Prompt` (new) enacting a voice is the norms slice's
`gmeow:Persona` (registers, activation `Condition`, `StyleGuide`) applied at
prompt-assembly time. The seam stays instance-level until the projection that
assembles prompts from personas lands extension-side.

## 6. Memory is claims, not vectors

`gmeow:MemoryItem` (new gufo:Role ⊑ Observation): any claim can be remembered;
revision is supersession + `gmeow:displayable false` (P10); salience rides the
EXISTING statement-level `gmeow:importanceLevel`; recency rides the statement
clocks. Recall is a retrieval (this slice's `RetrievalEvent`, §"Terms" below).
This is the substrate under the `gmeow` client and the MCP store/recall/revise
triad.

### Joining claim memory and objectual remembering

`MemoryItem` is a role on an existing observation or claim, not a second copy of
its content. `memoryOf` names the remembering agent. In contrast,
[`remembers`](../cognition/docs.md#remembered-subjects-and-remembered-claims)
links an agent to a remembered subject. Record each assertion explicitly rather
than deriving one from the other:

```turtle
@prefix gmeow: <https://blackcatinformatics.ca/gmeow/> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix ex: <https://example.org/> .

ex:alex a gmeow:Agent ;
    gmeow:remembers ex:conference .

ex:visitClaim a gmeow:MemoryItem ;
    gmeow:memoryOf ex:alex ;
    gmeow:memoryKind gmeow:memoryKindEpisodic ;
    gmeow:vantage ex:alex ;
    gmeow:observedFeature ex:conference ;
    rdf:reifies <<( ex:alex ex:attended ex:conference )>> .
```

The record has an explicit feature of interest and preserves the original claim.
This audit query joins existing assertions; it does not infer remembering from
syntactic mention:

```sparql
PREFIX gmeow: <https://blackcatinformatics.ca/gmeow/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
SELECT ?agent ?subject ?memory ?s ?p ?o WHERE {
    ?agent gmeow:remembers ?subject .
    ?memory a gmeow:MemoryItem ;
        gmeow:memoryOf ?agent ;
        gmeow:observedFeature ?subject ;
        rdf:reifies <<( ?s ?p ?o )>> .
}
```

The example assumes one admitted context. Apply the consumer's graph,
standpoint, time and display policy before this join; it is not a complete
recall policy. Suppression with `gmeow:displayable false` retains historical
claims and does not itself erase triples or make every unrestricted query hide
them. Neither a remembered claim nor a `remembers` edge asserts that the claim
is true, that every mentioned entity is remembered, or that the remembered
subject is a memory-record object.

## 7. Teleology

Agents have `gmeow:hasGoal`; an `gmeow:Intention` `gmeow:motivates` a
`gmeow:ModelInvocation` (an Activity ⊑ Event) — whose reading of the motive it
is rides `accordingTo` on the statement, like every attributed-motive claim.

## The spine (EvidenceSpan audit machinery preview)

```text
source ─(chunkOf)─ Chunk ─(spanOfChunk)─ EvidenceSpan ─(groundedIn⁻¹, polarity)─ claim node
                                                       (StandpointClaim, vantage = model,
                                                        wasGeneratedBy = ModelInvocation)
```

GraphRAG-specific pipeline observability around this spine — corpus, extracted
entity/relationship, community, and index-wiring artifacts — is
`extensions/graphrag` (consumer: Project Lillith). The generic vector/embedding
primitives that any embedding consumer needs — `Embedding`, `VectorIndex`,
`DistanceMetric`, `RetrievalEvent` — are core-tier terms owned HERE (see
"Terms" below), reused by both `extensions/graphrag` and
`extensions/embedding-projection` rather than duplicated per extension.

## Terms

The genuinely-new terms this slice mints, anchored to the doctrine above.

### gmeow:Chunk · gmeow:chunkOf · gmeow:spanStart · gmeow:spanEnd

The retrieval segment: a `gmeow:Chunk` is a contiguous slice of a source
information object, located in it by `gmeow:chunkOf` (functional, ⊑ `partOf`)
plus the integer offsets `gmeow:spanStart`/`gmeow:spanEnd` (zero-based, half-open
code points). The one genuinely missing information-object kind in the
source → Chunk → EvidenceSpan → claim spine.

A Chunk's `contentDigest` uses the mathematics-grounded `blake3_256Digest`,
`sha256Digest` or `md5Digest` datatype with lowercase hexadecimal text and no
algorithm prefix. Several algorithms may coexist, with at most one distinct
value per algorithm. The literal describes the Chunk's exact supplied bytes;
span coordinates remain Unicode code points and do not imply an encoding or
canonicalization. A digest of a canonical document identifies that canonical
artifact, rather than another serialization. The research-object `digests`
ItemList retains every admitted algorithm, datatype IRI and lexical value.

### Chunks and narrative segments

`Chunk` records retrieval segmentation; `ContentSegment` records structural
membership in a work. Neither role implies the other: an arbitrary retrieval
window need not be an authored scene or paragraph, and a narrative segment need
not be a retrieval unit. There is no universal `Chunk` subclass of
`ContentSegment`.

When one node really serves both roles, type it as both, retain `chunkOf` and its
source offsets, and record its document structure through `segmentOf` and
`segmentType`. An event can then point to that node with `narratedIn` without
widening its `ContentSegment` range. Two type assertions express two real roles;
they do not require duplicate nodes. See the
[refinement example](../observations/examples/refinement-readings.ttl).

### gmeow:spanOfChunk · gmeow:groundedIn · gmeow:supportPolarity · gmeow:SupportPolarity

The evidence seam: `gmeow:spanOfChunk` pins an `EvidenceSpan` into the retrieved
chunk; `gmeow:groundedIn` (domain-free, per the unified observation stance) ties
any claim node to a supporting span, and a claim with none is a flagged
hallucination (P10, never deleted); `gmeow:supportPolarity` records the NLI/AIS
stance from the closed three-value `gmeow:SupportPolarity` (supports / refutes /
neutral).

### gmeow:ModelInvocation · gmeow:usedModel · gmeow:hasPrompt · gmeow:samplingTemperature · gmeow:samplingTopP · gmeow:samplingMaxTokens

The model-invocation activity, provenance anchor of every generated claim: one
call to a model agent (`gmeow:usedModel`), carrying its prompts
(`gmeow:hasPrompt`) and sampling regime (`gmeow:samplingTemperature`,
`gmeow:samplingTopP`, `gmeow:samplingMaxTokens`). Outputs hang off the existing
`gmeow:wasGeneratedBy`; no forward output property is minted (P5).

### gmeow:Prompt · gmeow:PromptTemplate · gmeow:filledFrom · gmeow:promptRole · gmeow:PromptRole

The prompt artifact: a `gmeow:Prompt` is the concrete instruction presented to a
model — content-addressed and role-tagged (`gmeow:promptRole`, drawn from the open
`gmeow:PromptRole` vocabulary of system/user/assistant/tool). A
`gmeow:PromptTemplate` is the reusable, versioned, variable-bearing source a
concrete prompt links back to via `gmeow:filledFrom`.

### gmeow:ModelCard · gmeow:describesModel · gmeow:modelProvider · gmeow:modelVersionTag · gmeow:modelContextWindow · gmeow:modelTrainingCutoff

The model card: a structured document `gmeow:describesModel` the `SoftwareAgent`,
carrying `gmeow:modelProvider`, `gmeow:modelVersionTag`,
`gmeow:modelContextWindow`, and `gmeow:modelTrainingCutoff`. The card is about the
agent; capability claims stay attributed, contestable claim-layer observations.

### gmeow:Contradiction · gmeow:contradictsClaim · gmeow:detectedBy · gmeow:contradictionKind · gmeow:ContradictionKind

The surfaced contradiction: a relator binding two or more claim nodes in conflict
(`gmeow:contradictsClaim`), attributed to its detector (`gmeow:detectedBy`) and
kind-classified (`gmeow:contradictionKind` over the open `gmeow:ContradictionKind`
— factual / temporal / numeric / framing). It surfaces conflict, never resolves it
by rank (P9).

### gmeow:MemoryItem · gmeow:memoryOf · gmeow:memoryKind · gmeow:MemoryKind

The memory role: a `gufo:Role` on the universal claim construct — any claim can be
remembered. `gmeow:memoryOf` names the remembering agent and `gmeow:memoryKind`
its cognitive register (open `gmeow:MemoryKind` — episodic / semantic / working /
procedural). Revision is supersession + `gmeow:displayable false` (P10), never
deletion.

### gmeow:Embedding · gmeow:embeddingOf · gmeow:embeddingModel · gmeow:embeddingDimensions · gmeow:DistanceMetric · gmeow:distanceMetric

Promoted here (from `extensions/graphrag`) as a core-tier, shared vector
primitive: a vector representation of an information object (usually a
`Chunk`), produced by an embedding model — the genuine vocabulary gap in the
semantic-web stack. `embeddingOf` (functional) names the represented object;
`embeddingModel` (functional) the producing agent, so two models' embeddings
of the same object are two individuals (P9); `embeddingDimensions` the
dimensionality; `distanceMetric` (functional, domain-free — carried by
`Embedding` and `VectorIndex` alike) the open `DistanceMetric` vocabulary
(cosine, dot product, euclidean) an embedding or index is meaningful under.
`extensions/graphrag`'s `gmeow:vectorRef` still points the payload outside the
graph (P12); this slice mints only the vector's provenance, never the floats.
`extensions/embedding-projection`'s pack-level `gmeow:EmbeddingProjection`
aggregates many `Embedding` rows (`gmeow:aggregatesEmbedding`) rather than
subclassing this one.

### gmeow:VectorIndex · gmeow:RetrievalEvent · gmeow:againstIndex

Promoted here (from `extensions/graphrag`) as core-tier, shared retrieval
primitives: `VectorIndex` is a built retrieval structure over a corpus's
embeddings (`extensions/graphrag`'s `gmeow:indexAlgorithm`/
`gmeow:indexParameters`/`gmeow:indexesCorpus` still carry its build details);
`RetrievalEvent` is one retrieval against a vector index — the query, the
index queried (`againstIndex`, functional), and the chunks returned
(`extensions/graphrag`'s `gmeow:retrievedChunk`/`gmeow:retrievalScore`/
`gmeow:forQuery` carry the rest) — an agent-memory recall is a RetrievalEvent
too (§6 above). `extensions/embedding-projection`'s `gmeow:DerivedVectorIndex`
specializes `VectorIndex` directly as a non-authoritative, rebuildable
accelerator.

## Keeping a model consultation in its own words

`promptText` retains the words of a concrete Prompt, including supplied language
and direction. Its `rdfs:Literal` range admits both RDF 1.2 language literal forms;
it does not restrict text to xsd:string or to nondirectional language strings.
`modelAlias` is the requested `xsd:token` provider name, while `usedModel` continues
to identify the actual SoftwareAgent. Preserve both when an alias is resolved.
`externalRedactionCount` records the reported number of redacted answer items as
`xsd:nonNegativeInteger`. Explicit zero means none reported redacted; an absent
count means the record does not supply that information. Do not invent the hidden
content or treat this count as a character count.

An answer is an InformationObject with `answerText`, `wasGeneratedBy` pointing
back to ModelInvocation, `wasAttributedTo` naming the model, and `wasDerivedFrom`
for the cited sources actually used. An Observation of the consultation reaches
that answer through the existing individual-valued `observationResult`; raw answer
text is never placed on that object property. The observer's receipt and the
model's answer attribution stay distinct. The words are preserved content, not
asserted truth: any claim extracted from them needs its own attributed observation
and evidence. `answerText` also admits supplied language and direction.

The [consultation record](examples/consultation-record.ttl) keeps the question,
requested alias, actual model, original answer, three cited sources and redaction
count together, with a separate explicit-zero example. Content-addressing and exact
byte provenance use the existing source machinery; these text properties do not
replace an original byte digest or specify a new digest algorithm.

## Literal language and direction

The natural-language fields `gmeow:modelProvider` admit
plain text with unspecified language, language-tagged text, and RDF 1.2 directional
text. Supplied public or private-use language tags remain part of the literal.
The canonical value restrictions derive the validation view; they do not add a
closed-world requirement for an explicitly asserted subject type. A machine key,
source expression, or byte payload uses its own declared property and datatype.
See [literal policy](../../../docs/LITERALS.md) for the shared contract.

## General classifier evidence

`ClassifierOutput` records an attributed score for an exact external
`ClassifierLabel` in a `ClassifierLabelSet`, including genre and zero-shot
classification. Shared run provenance and score/decision vocabulary are owned
here; affect retains its class specializations and affect-only laws.
`ModelInferenceRun` is an enduring execution record compatible with the
observation vantage contract. See [the contract and example](design/CLASSIFIER-EVIDENCE.md)
for candidate-set scope, calibration and the separate execution-activity boundary.

## Contract-bound chunkings and summary carriers

`Chunking` records one segmentation of an exact source revision under an
identified rules artifact. `ChunkingMember` selects actual chunks with scoped
ordinals. `BlockExtent` places atomic ContentBlocks in the same whole-source
coordinate frame as the chunks, enabling intrinsic no-split and coverage laws.
Selected source and contract digests identify those artifacts’ own bytes and
match the complete typed literal on each named artifact. A matching hexadecimal
string under another algorithm datatype does not satisfy a pin. The source,
contract and ordered member tuple is distinct from any scheme identifier built
from it. The local digest restrictions leave the global `contentDigest` range
unchanged. Overlap and exhaustive coverage follow the declared contract without
defaults.

`chunkingRulesArtifact` identifies the actual rules artifact included in the
creation context; `chunkingContractDigest` pins its selected content digest.
The embedding extension’s `chunkingContract` instead carries an opaque literal
configuration reference on an `EmbeddingFamily`. These are separate properties
with distinct domains and value kinds, without an alias or inferred conversion.

A retrieved summary’s `chunkOf` names the carrier containing its text, while
`wasDerivedFrom` names the summarized division. A generated summary is not a cut
of its original division. Summary and Chunk can share a node when both meanings
hold; separate summary and retrieval-chunk nodes are also valid. CommunitySummary
keeps its GraphRAG community meaning. See [the contract and ordinary scenes](design/CHUNKING.md).

## Records held among prose

A `HeldRecord` is an occurrence of a machine record removed from one source
text and decomposed into facts. `textHeldRecord` connects the exact text
occurrence to each removed record. A labelled text facet is one suitable
carrier: its `facetText` retains the surrounding words, while other decomposed
fields reuse `hasFacet`, `LabelledFacet` and `entryOrdinal`.

The original zero-based, half-open `spanStart`/`spanEnd` pair counts Unicode
code points before extraction. Both are required single nonnegative integers,
with start strictly before end. The original span is never checked against the
shortened retained text, and an original source length is not fabricated.
One held occurrence belongs to one text occurrence; identical content in
different texts remains separate occurrences.

`heldContentStatement` supplies the distinguished content as an actual RDF 1.2
triple term. Keep the identical explicit `rdf:reifies` link on the held record:
current statement-metadata extraction reads that established predicate, not a
new alias inferred later. The canonical binding law joins the same graph term
in both roles, and COUNT DISTINCT requires one distinguished term. A separate
evidence law covers the aggregate's zero-row case and requires a containing text.

The retained surrounding words are verbatim, but the removed record's own text,
whitespace, escapes and key order are absent. Original text therefore cannot be
rebuilt exactly. The content statement and other fields are facts supplied by
the producer or importer; quotation alone does not assert the quoted content.
The [ordinary intake scene](examples/record-intake.ttl) includes an
explicitly asserted content fact separately from its reifier.

These source contracts do not parse serialized records, prove decomposition
fidelity or introduce a generic triple-term node-kind validator. They retain
actual RDF 1.2 syntax and explicit reifier evidence through the existing path.
Use the established type and subproperty closure before inherited facet
validation, and completed statement-metadata lowering before its component
binding laws. No execution or authenticity is claimed by the declarations.

## Reported analysis inputs

An existing `lang:Analysis` can retain the supplied context of the unit it
read without becoming an input text artifact or model invocation.

| Property | Descriptive input context |
| --- | --- |
| `analysisFirstChunkKey` | Supplied first source-chunk integer key. |
| `analysisLastChunkKey` | Supplied last source-chunk integer key. |
| `analysisChapterKey` | Supplied integer chapter or grouping key affecting selection. |
| `analysisChunkKeyFrame` | Supplied string describing the source-key namespace or indexing convention. |
| `analysisInputConstruction` | Supplied string description of assembly conventions, retaining language and direction. |
| `analysisSourceContext` | An actually identified source InformationObject associated with the keys or selection. |

These fields are optional. The first, last and chapter keys are individually
at most one per Analysis; frame and construction descriptions and
source-context links can coexist as supplied. Unknown conventions and missing
metadata stay absent. The literal properties specialize `lang:literalValue`.

Reuse `hasGranularity` with the open individuals `granularityChunk`,
`granularityPassage` and `granularityChapter`. These are resolution values,
not per-level classes, fixed text sizes or a universal `coarserThan` ladder.
Other attributed granularity values remain coequal.

A source key is not a ChunkingMember's zero-based `entryOrdinal` or a
`spanStart`/`spanEnd` code-point bound. The descriptors impose no global key
origin, inclusive or exclusive endpoint convention, continuity or numeric
ordering. They do not establish that a carried retrieval chunk contains the
original analyzer input.

Construction prose is not an executable profile or historical-byte witness.
A source-context link requires no invented artifact or digest. These fields
retain the reported unit's context; they do not reconstruct input text,
authenticate its bytes or perform coordinate conversion.

## Containing source divisions

`chunkInDivision` names a supplied ContentSegment containing the whole
particular occurrence of source content represented by a Chunk. It records
an attributed containment claim, rather than an arbitrary association or a
division that contributes only some of the chunk's content. Identical wording
elsewhere is a different occurrence.

The relation is optional and nonfunctional. Genuinely containing nested
divisions may coexist without a unique or nearest choice. When the supplied
section and chapter both contain the whole occurrence, retain both claims:

```turtle
ex:chunk a gmeow:Chunk ;
    gmeow:chunkOf ex:source ;
    gmeow:chunkInDivision ex:section, ex:chapter .
```

Keep the actual source, segmentation context and each assertion's actual
viewpoint. The snippet shows the division links alongside the unchanged
carrier relation; the chunk's existing span and source obligations still
apply. A chunk crossing two child divisions may name a supplied common
container only when it contains the whole occurrence. Neither merely
intersected child qualifies. Keep an unknown container absent.

`chunkInDivision` specializes broad `partOf` for this containment of source
content. It does not specialize `chunkOf`, `segmentOf` or `blockOf`, change
the coordinate origin, or infer a structural segment type for the Chunk.
The specialized relation has no transitive characteristic or ancestor-selection
chain. Recorded containment neither proves geometry nor selects a nearest
ancestor, converts coordinates or authenticates bytes.

A generated summary's original subject division is not automatically a
container of the summary's actual text. Keep that subject and derivation
separate from the actual carrier and any genuine containing division
(Principles 2, 4, 9, 17 and 19).

## Whole-work analysis input resolution

Use `granularityWork` through the existing `hasGranularity` when a source
explicitly reports an analysis input at whole-work resolution. It extends the
open text-unit values already supplied for chunk, passage and chapter input.
Other attributed resolutions can coexist without a preferred value.

```turtle
ex:analysis a lang:Analysis ;
    gmeow:hasGranularity gmeow:granularityWork .
```

This states the reported resolution of the selected input. It does not identify
an abstract Work, a particular realization or the text carrier. A Work survives
changes of language, edition and copy; those are not interchangeable input
identities. Reading a whole file or document does not by itself establish that
the input was reported at whole-work resolution.

Keep any supplied `analysisSourceContext`, source-chunk keys, key-frame,
chapter-key and `analysisInputConstruction` descriptors separately. These
fields remain optional, and unknown source conventions remain unknown. The
granularity value neither reconstructs historical input bytes nor authenticates
complete source coverage or consumption of every realization of the work.

No fixed text size, source selection, default, required metadata or universal
`coarserThan` relationship follows from this value. Existing Chunk and Chunking
carrier, source, extent and digest obligations remain in force (Principles 4,
9, 11 and 19).

## Reported chunker descriptors

`chunkerName` and `chunkerVersion` retain the exact supplied name and version
wording on a Chunking. Both are optional and nonfunctional. Preserve each complete
string and its supplied language or direction; unknown wording stays absent.
These labels do not identify an executable implementation or define a version
grammar, and equal names or versions do not identify the same algorithm.

`chunkerParameters` links the result to a supplied `StructuredMap` occurrence.
Its entries use existing `hasFacet`, `LabelledFacet`, `facetLabel` and
`facetText`, so keys and complete descriptive strings remain queryable:

```turtle
ex:segmentation gmeow:chunkerName "Outline cutter" ;
    gmeow:chunkerVersion "edition amber" ;
    gmeow:chunkerParameters ex:parameters .
ex:parameters a gmeow:StructuredMap ; gmeow:hasFacet ex:entry .
ex:entry a gmeow:LabelledFacet ;
    gmeow:facetLabel "section policy" ;
    gmeow:facetText "Keep headings together." .
```

The snippet illustrates descriptors; the existing result's source, frozen rules
artifact, digest pins and granularity obligations remain in force. Descriptions
neither replace that artifact nor certify that a chunker ran or that an external
parameter inventory was completely imported.

Within each selected map, every entry requires descriptive `facetText` and an
exact `xsd:string` key. Different entry occurrences cannot share the same complete
RDF key term in that map. A conflict is retained and reported, never resolved by
merging entries or choosing a last value. The same key in different maps remains
independent. Generic maps and label-only facets keep their existing semantics.

Preserve empty keys and strings. A supplied typed empty map has no entries;
an absent map makes no empty-map assertion. Retain original case, spacing and
punctuation without token retyping, number extraction, unit assignment or
invented ordinals. Transport sorting is not source order. Several attributed
name, version and map claims do not create a cross-product identity or pairing.

The [chunking design](design/CHUNKING.md#reported-chunker-descriptors) records
the scoped laws and the existing first-class map model (Principles 2, 4, 9, 11,
12, 17 and 19).

## Regression output semantics

Use `scoreRegression` through the existing `scoreSemantics` when a model emits
a scalar regression prediction for the output dimension identified by its
actual `emittedLabel`. Retain that exact ClassifierLabel and its label-set
membership; it is an external output identity, not a canonical category or
mathematical dimension.

Keep the raw `classifierScore` as the existing decimal carrier, with the actual
`classifiedTarget`, `producedBy` ModelInferenceRun, model identifier and revision,
recorded input and source attribution. The new semantics adds no universal
range, scale, unit, unit interval, calibration, confidence or evidence-strength
interpretation. A value between zero and one does not establish probability.
Comparison or interpretation under a particular scale still needs its actual
source and frame; do not invent missing context (Principles 9, 11 and 19).

This individual implies no argmax, threshold, activation function or workflow.
Any actually supplied decision policy remains separate; existing label-set and
run obligations remain in force. A model score is not an actual quantity
measurement, and this value does not turn the score or its output into a
`math:Quantity`.

The current native affect capture/recovery API does not admit `scoreRegression`.
This vocabulary value does not extend that adapter or enable model execution.
It supplies the canonical score meaning; runtime support requires its own
implementation and qualification.

## Reported classifier and measurement inputs

### gmeow:ChunkSpan

A ChunkSpan identifies the selected source-text content unit reported as input
across source chunks. The classifier's classifiedTarget and a Measurement's
observedFeature can name that unit when both records actually concern the same
input. The unit is separate from each output, the model-run record, the metric
and the resulting Quantity. Do not put descriptors on an output and then name
that output as the content that was read.

Use the actual supplied unit identity. Endpoint integers, equal wording and
granularity do not establish identity across source, grouping, assembly or
producer contexts. ChunkSpan specializes the existing EvidenceSpan category and inherits
InformationObject, reusing the common anchored-target model without requiring
historical input bytes. It does not classify an input descriptor, a structural
division, a mathematical set or an execution event.

This category reuse does not assert Selector typing or require citation
selectors, spanOfChunk, code-point offsets, support polarity or digests.
Separately supplied anchoring facts retain their existing domain and validation
contracts; a source key is not automatically a citation selector or offset.

If the actual input already is a Chunk, reuse that identity and its complete
existing contract. Do not wrap every Chunk or add ChunkSpan as a second ultimate
Kind to a Chunk or ContentSegment. A reported source-key range alone does not
establish the contiguous cut, carrier and coordinate facts required by Chunk.

The optional domain-specific roles preserve supplied selection context:

| Property | Supplied descriptor |
| --- | --- |
| chunkSpanFirstKey | First source-chunk integer key. |
| chunkSpanLastKey | Last source-chunk integer key. |
| chunkSpanChapterKey | Integer chapter or chapter-group key affecting selection. |
| chunkSpanKeyFrame | String describing the source-key namespace or indexing convention. |
| chunkSpanConstruction | Assembly description retaining its complete literal, language and direction. |
| chunkSpanSourceContext | Actually identified source InformationObject associated with the selection. |

Only first, last and chapter keys are locally at most one per coherent ChunkSpan.
The roles remain globally nonfunctional. Attributed frame descriptions,
construction descriptions and source-context links may coexist. Retain every

integral number of gram positions under the actual segmentation/counting

## Reported source presentation

The AI slice records applied extraction and chunker reports alongside its
existing block extents and source-analysis descriptors. `blockHtml` retains
the exact reported HTML source string on a ContentBlock. It is machine markup
stored as `xsd:string`; reporting it makes no DOM, Rendering, sanitization or
execution claim. The block’s existing structural obligations remain in force.

On an actual Chunk, `chunkSectionTag` retains the reported `xsd:string` section
tag. `chunkChapterHeading`, `chunkSectionHeading` and `chunkSubsectionHeading`
retain the three distinct reported heading roles as complete word literals:
`xsd:string`, `rdf:langString` or `rdf:dirLangString`. Language and direction are
preserved when supplied; no language is guessed. The roles do not infer heading
depth, hierarchy, structural divisions, source offsets or containing chapters.

`chunkMarkerLines` selects a StructuredSequence. Each supplied marker has its

ChunkMarkerLineTextConstraint additionally requires a string scalar for every
selected item. Its ordinary Formula generates procedural validation; no new
native failure class or reasoner-discharge claim is added.

All six report roles are optional and nonfunctional. Keep their actual
exact-statement source and viewpoint. A supplied empty sequence is represented
explicitly only when actual evidence establishes it. An omitted relation makes
no empty or null assertion, and a schema default does not prove historical field
presence. These descriptors leave the Chunk’s carrier, extent, digest and
chunking contracts unchanged (Principles 4, 9, 17 and 19).
