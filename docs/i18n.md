# Internationalization (i18n) workflow

GMEOW uses a **compiled PO layer** for translations. Committed `.ttl` and `.md`
files stay English-only; translations live in gettext `.po` files and are folded
into the `gmeow.gts` bundle at build time. This keeps canonical sources small,
diffs readable, and translation reviews independent of ontology engineering.

## File layout

| What | Where |
|---|---|
| Term translations | `slices/<group>/<name>/i18n/<lang>.po` |
| Markdown POT templates | `dist/i18n/docs/<rel-path>.pot` (generated) |
| Ontology-docs template POT | `dist/i18n/ontology-docs-templates.pot` (generated) |

Term PO files are committed; everything under `dist/i18n/` is a generated,
ephemeral build product and is never committed.

## Translation keys

Ontology term entries are keyed by the subject IRI and predicate that carry the
English source string:

```po
#: https://blackcatinformatics.ca/gmeow/slices/Entity
msgctxt "https://blackcatinformatics.ca/gmeow/Entity|http://www.w3.org/2000/01/rdf-schema#label"
msgid "Entity"
msgstr "Entité"
```

Markdown segments use `msgctxt = "<rel-path>|<anchor-hash>"` and ontology-docs
template strings use `msgctxt = "ontology-docs-template|<id>"`. Those forms are
produced automatically by the extract commands below.

## Commands

All i18n commands are developer-only because they need the `slices/`, `dsl/`,
and `generated/` source trees:

- `gmeow-dev i18n extract [--output-dir DIR] [--lang LANG]`
  Refresh POT templates (or seed empty `.po` files for *LANG*) from the merged
  English ontology, slice guides, project docs, and ontology-docs templates.
  Language catalogs are emitted with empty `msgstr` values; extraction never
  copies English into a translation slot.

- `gmeow-dev i18n lint [--max-fuzzy-ratio PERCENT]`
  Reject malformed catalogs and mechanically detectable translation corruption,
  including copied multi-word English, hybrid English prose, and Chinese prose
  with no Han characters. Single-word cognates and notation-only technical
  invariants remain admissible.

- `gmeow-dev i18n merge [--output FILE] [--lang LANG]`
  Fold committed `.po` translations into the merged English graph and emit a
  single multilingual Turtle file without touching canonical sources.

- `gmeow-dev i18n export-csv [--output FILE]`
  Export all committed `.po` catalogs to a flat CSV file for spreadsheet-based
  translation workflows.

- `gmeow-dev i18n export-xliff [--output FILE]`
  Export all committed `.po` catalogs to an XLIFF 1.2 file for translation
  memory tools.

- `gmeow-dev i18n sync-english [--dry-run]`
  Update English canonical `.ttl` and `.md` sources from `en.po` catalogs. This
  is the inverse of `extract --lang en` and is used when English strings are
  edited in translation tooling.

## Translator workflow

1. After English edits, run `gmeow-dev i18n extract` to refresh the POT files in
   `dist/i18n/`.
2. Use `msgmerge` or manual copy-paste to update the committed `.po` files;
   mark changed or uncertain entries `#, fuzzy`.
3. Commit **only** `.po` files; never commit translated `.ttl` or `.md`.
4. Run `make i18n-lint` and `make validate` before pushing. The i18n lint warns
   about orphaned entries, fails an entirely fuzzy catalog, and hard-fails
   mechanically corrupted non-empty translations.

## Quality gates

The normal GMEOW gate sequence covers the i18n layer:

- `make i18n-lint` — parses PO files, checks `msgctxt` keys against the merged
  English graph, enforces translation integrity, and enforces the all-fuzzy
  catalog rule.
- `make validate` — validates the authored RDF and shape surfaces.
- `make sync` — rebuilds every committed generated artifact; the
  multilingual bundle surfaces are produced here.
- `make sync SYNC_MODE=check SYNC_OUTPUTS=generated` — ensures no drift between canonical sources and
  generated outputs.
- `make constitution-check` — verifies that every constitutional principle has
  a live enforcement test.

Run the full sequence with `make check` (or the Docker-free subset
`make install fmt lint validate sync constitution-check test-fast`
when the heavy reasoner lanes are unavailable).

## Known scope deviations

The approved implementation for this layer (Option A) intentionally deviates
from the original specification in two ways:

- **Custom Markdown splitter instead of po4a.** The extractor uses a small,
  deterministic paragraph-level Markdown splitter implemented in
  `gmeow_tools.i18n_catalog`. It does not depend on `po4a`, which keeps the
  developer toolchain inside the existing Python/uv environment and makes the
  segment hashes stable across host systems.

- **`sync-english` is included as a convenience.** The original specification listed re-importing
  English strings from translation tooling back into canonical `.ttl`/`.md`
  sources as out-of-scope. The `gmeow-dev i18n sync-english` command is provided
  anyway because it is the natural inverse of `extract --lang en` and makes
  English-only edits in PO-aware tooling round-trip safely.
