## Answers to the coordinator's questions

**(1) `mint_order`.** Each step takes the first waiting tuple, in sorted reifier order, whose arguments name no tuple still waiting. That is a topological order chosen greedily by sorted name.
- Chains of depth three or more: correct. Each link becomes ready only after the tuple it takes has been removed.
- A tuple taking two other tuples' nodes: correct. It waits for both.
- A diamond: correct.
- Self-reference: `naryArg_i(R, R)` keeps R waiting on itself, so no tuple is ever ready and the head is refused as a cycle. Correct.
- No nesting: every tuple is ready at once, so position 0 is taken each step and the order is exactly sorted order, as before. The same holds for any nested head whose dependencies already sort first, which is the only kind of nested head the old code could execute. By induction the removed set is always a prefix of the sorted list, so the first waiting tuple is always ready. The bindings are therefore pushed in the identical order.

Byte identity holds by construction. A tuple's IRI is `mint_nary_reifier(relation, its own ordered argument values)`, and mint order only decides whether those values are bound yet. This delta changes neither the relation, the argument order nor the value-null ordinals.

The chase tests compare against `mint_nary_reifier` itself, so they show self-consistency, not byte identity. Recorded values exist only for the mint function: provenance.tests.rs:345, 360, 379 (`mint_nary_reifier_golden_{a,b,c}`), which passed in `r2-nextest-logic.log`. No recorded value pins which inputs the chase passes to the mint. That would matter only if argument selection changed, and it did not.

### R3 (REQUIRED): an authored existential-rule record whose head the chase refuses still ends in exit 5; box 3 requires a named drop and `not-decided`

- What happens: the record is prepared in `PreparedChaseRule::from_source` (seminaive/joint/input.rs:541, chase.rs:323-338). That raises `RefusedRuleHead`. prove.rs `native_leg` turns it into `NATIVE_EXECUTION_FAILED` with exit 5 (prove.rs ~998-1015).
- `prove_cli.rs::an_engine_failure_reports_the_selection_and_the_drops_named_before_it` asserts this outcome.
- Under the README's exit-code table and the issue's problem statement and box 3, this input is a shape the engine cannot carry. It is not a broken invariant. See ruling (4).
- Required outcome: a selected record whose head the chase refuses gives a named drop carrying the `RefusedRuleHead` text (rule IRI and head relations) and `not-decided`, exit 3 under `--gate`. It must not be exit 5.
- Mechanism is the coder's choice. One option: drop the record rule as residue during source preparation and run the rest, matching the formula path. Another: have `native_leg` map a `RefusedRuleHead` to a drop with a `refused` native leg, as it already does for `NativeRefusal`.
- Retarget the CLI test to that outcome. Keep box 4 on the unit test, unless an honest resource-limit input is found.

### R4 (REQUIRED): the new README sentence says a post-engine failure "replaces only its verdict"; it replaces more

- README.md:323-325. `ProveReport::execution_failure` (prove.rs:381-392) also rewrites `decision`, `evaluation_status` (to `failed`), `completeness` (to `unknown`), `information_state` (to `not-evaluated`), `evidence_grade` and `gate_admission`, and it appends a diagnostic.
- "Only its verdict" is therefore false. A false claim in the docs is a defect under AGENTS.md § 4.
- The fix is wording, for example: "keeps the completed selection and engine blocks and replaces the verdict and decision fields, adding the failure diagnostic".
